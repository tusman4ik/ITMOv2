## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр динамического списка сгенерированных задач №16 (Priority: P1) 🎯 MVP

Ученик открывает интерфейс тренировки по Заданию №16. На экране динамически отображается список сгенерированных задач различных прототипов (16-001..16-005, 16-999). Для выбранной задачи отображается её тип, метаданные (идентификатор прототипа, зерно генерации) и полное условие с таблицей примеров входных/выходных данных. Ученик может переключаться между задачами и генерировать новые варианты на лету.

**Why this priority**: Отображение динамически созданных условий с наглядным форматированием — ключевая функция клиентского интерфейса, без которой невозможно начать решение задач.

**Independent Test**: Пользователь открывает интерфейс, видит список задач №16, выбирает прототип и видит отрендеренное условие задачи с таблицей примеров.

**Acceptance Scenarios**:

1. **Given** открытая страница задач, **When** пользователь выбирает задачу из списка, **Then** система отображает условие задачи, параметры генерации и таблицу контрольных примеров.
2. **Given** список задач, **When** пользователь нажимает кнопку создания нового варианта, **Then** в интерфейс добавляется новый экземпляр задания без перезагрузки всей страницы.
3. **Given** сбой сетевого запроса к сервису генерации, **When** загрузка не удалась, **Then** пользователю показывается понятное сообщение об ошибке с кнопкой повторной попытки.

### User Story 2 - Ввод и отправка программного кода решения (Priority: P2)

Ученик переходит к решению выбранной задачи. Интерфейс предоставляет удобный редактор для ввода исходного кода программы (с поддержкой подсветки синтаксиса и базового форматирования для языка Python). Ученик вводит решение и нажимает кнопку «Отправить на проверку». Интерфейс подтверждает отправку, переходит в состояние ожидания и блокирует повторные случайные нажатия до завершения обработки.

**Why this priority**: Редактор и сценарий сдачи кода образуют основной интерактивный шаг обучающегося.

**Independent Test**: Пользователь вставляет код решения в редактор, нажимает «Отправить» и видит визуальный индикатор активной проверки.

**Acceptance Scenarios**:

1. **Given** выбранная задача с формой кода, **When** пользователь вводит текст решения и нажимает «Отправить», **Then** отправляется запрос на проверку и отображается индикатор «Проверка выполняется...».
2. **Given** пустой редактор кода, **When** пользователь нажимает кнопку отправки, **Then** система выдает предупреждение о необходимости ввести решение и не выполняет сетевой запрос.
3. **Given** процесс проверки, **When** запрос находится в обработке, **Then** кнопка отправки решения временно блокируется во избежание дублирующих отправок.

---

### User Story 3 - Визуализация результатов и потестового протокола проверки в режиме fail-fast (Priority: P3)

После завершения асинхронной проверки кода в песочнице интерфейс автоматически обновляется и показывает ученику вердикт: набранные баллы (0..2), итоговый статус (успех, неверный ответ, ошибка времени выполнения, таймаут) и детализированную таблицу тестов. 
Проверка выполняется в строгом режиме **fail-fast**: тестирование останавливается на первом непрошедшем тесте, последующие тесты не вычисляются. В таблице протокола проверки отображаются все выполненные тесты с их статусами, а для непрошедшего теста наглядно выводятся все ошибки и детали расхождения (входные данные, ожидаемый вывод, фактический вывод программы ученика, сообщение чекера, время исполнения и затраченная память), а также явная отметка о прерывании дальнейшего прогона.

**Why this priority**: Подробный протокол проверки дает ученику мгновенную обратную связь по первой встреченной ошибке, экономя время и ресурсы системы за счет остановки на первом сбое.

**Independent Test**: Запуск заведомо ошибочной программы (например, дающей неверный ответ на 2-м тесте) останавливает прогон на 2-м тесте, и интерфейс показывает ровно два выполненных теста: первый — OK, второй — с подробным описанием ошибки в таблице, последующие тесты не запускаются.

**Acceptance Scenarios**:

1. **Given** успешный вердикт проверки, **When** данные получены интерфейсом, **Then** отображается значок успеха, балл 2/2 и статус "Все тесты пройдены", в таблице отображаются все пройденные тесты.
2. **Given** решение, падающее на одном из тестов, **When** проверка завершается по политике fail-fast, **Then** исполнение останавливается сразу после ошибки, последующие тесты не вычисляются, а в таблице результатов отображаются все ошибки и расхождения упавшего теста.
3. **Given** ошибка компиляции или выполнения (Runtime Error / Crash), **When** отображаются результаты, **Then** пользователю в таблице и диагностическом блоке выводятся лог ошибки и стек вызовов для отладки.

---

### Edge Cases

- Что происходит при генерации большого списка задач (например, 20+ вариантов)? (Интерфейс должен использовать пагинацию или компактный список с прокруткой, не ломая верстку страницы).
- Что происходит при падении первого же теста в режиме fail-fast? (Прогон завершается немедленно, в отчете отображается единственный выполненный тест с полной детализацией ошибки и итоговый балл 0).
- Что происходит при потере интернет-соединения во время ожидания вердикта? (Интерфейс сообщает о потере связи и предлагает обновить статус проверки вручную).
- Что происходит при вставке очень длинного кода или непредвиденных символов? (Редактор корректно сохраняет отступы и кодировку UTF-8).
- Как отображаются длинные выводы программы в протоколе тестов? (Вывод ограничивается компактным блоком с внутренней прокруткой).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Интерфейс ДОЛЖЕН поддерживать отображение динамического набора вариантов Задания №16 (прототипы 16-001, 16-002, 16-003, 16-004, 16-005, 16-999).
- **FR-002**: Интерфейс ДОЛЖЕН позволять пользователю запрашивать генерацию одного или нескольких вариантов задач с возможностью задания количества и выбора прототипов.
- **FR-003**: Для каждого варианта задачи интерфейс ДОЛЖЕН корректно отображать текст условия (включая HTML-разметку, списки и таблицы примеров).
- **FR-004**: Интерфейс ДОЛЖЕН содержать область редактирования программного кода с поддержкой моноширинного шрифта, табуляции и подсветки синтаксиса для языка Python.
- **FR-005**: Интерфейс ДОЛЖЕН обеспечивать отправку решения на проверку с передачей идентификатора попытки (`attemptId`) и текста программы.
- **FR-006**: Интерфейс ДОЛЖЕН визуализировать статус ожидания проверки без блокировки просмотра условий других задач.
- **FR-007**: Система проверки ДОЛЖНА работать в режиме fail-fast (`STOP_ON_FIRST_FAILURE`): при падении любого теста прогон немедленно останавливается, последующие тесты не досчитываются.
- **FR-008**: Интерфейс ДОЛЖЕН отображать итоговые баллы и структурированный потестовый протокол в виде таблицы, где для каждого выполненного теста видны все ошибки, статус (OK/WA/TLE/RE), входные данные, реальный вывод, эталон и диагностические сообщения.
- **FR-009**: Интерфейс ДОЛЖЕН сохранять локальное состояние текущего введенного кода для каждой задачи при переключении между вариантами в рамках одной сессии.

### Key Entities *(include if feature involves data)*

- **Задача в интерфейсе (TaskCard)**: Содержит идентификатор задачи (`exam`, `subject`, `number`, `prototypeIdx`, `seed`), текст условия, таблицу примеров, статус решения.
- **Черновик решения (SolutionDraft)**: Связан с конкретной задачей, содержит текущий введенный код и выбранный язык программирования.
- **Отчет о проверке (VerificationReport)**: Содержит статус проверки, набранные баллы, количество пройденных тестов, список строк протокола с метриками (время, память, вывод) и лог ошибок.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Время первичного рендеринга условия задачи и примеров после получения данных не превышает 200 миллисекунд.
- **SC-002**: 100% сгенерированных HTML-условий задач и таблиц примеров отображаются без артефактов верстки на экранах шириной от 768px и выше.
- **SC-003**: При переключении между задачами в списке ранее набранный код пользователя сохраняется в 100% случаев.
- **SC-004**: В таблице протокола проверки отображаются все ошибки и расхождения выполненных тестов с подсветкой причины сбоя (WA, TLE, RE).
- **SC-005**: При наличии ошибки в решении тестирование останавливается ровно на упавшем тесте (fail-fast), последующие тесты не запускаются.

## Assumptions

- Frontend разрабатывается как SPA на React + TypeScript (Vite) в каталоге `frontend` с проксированием `/api` на `task-service` (`http://localhost:8081`).
- Бэкенд проверки (`code-runner` / `task-service`) использует политику `ExecutionPolicy.STOP_ON_FIRST_FAILURE` для режима fail-fast.
- Frontend взаимодействует с API `task-service` (`/api/v1/tasks/generate`, `/api/v1/tasks/recreate`, `/api/v1/tasks/check`).
- Основной язык решения задач №16 — Python.
- Динамический набор задач генерируется по запросу пользователя через бэкенд `spc-demo`.
- Все проверки кода происходят асинхронно в изолированной песочнице, клиент опрашивает статус или получает готовый вердикт.
