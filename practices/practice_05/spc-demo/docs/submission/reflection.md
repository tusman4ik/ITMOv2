# Рефлексия: Применение Spec Kit и контракт-ориентированная разработка (ДЗ 5)

## 1. Сравнение Spec Kit и OpenSpec

| Критерий | OpenSpec (из лекций/практик) | Spec Kit (применен в ДЗ 5) |
|---|---|---|
| **Управление структурой** | Набор артефактов `proposal/`, `design/`, `specs/`, `tasks/` | Шаблоны `spec.md`, `plan.md`, `tasks.md`, `contracts/` |
| **Управление правилами** | `rules` в `openspec/config.yaml` | Проектная конституция `.specify/memory/constitution.md` |
| **Ворота качества** | `openspec validate` (структурная валидация) | Чек-листы требований `checklists/requirements.md` + автоматические тесты |
| **Интеграция** | Отдельный CLI инструмент (`openspec`) | Git-нативный набор bash-скриптов и команд агента (`.specify/`) |

**Вывод**: Spec Kit предоставляет строгий процесс управления архитектурными ограничениями через единую конституцию проекта и встроенные фазы уточнения (`/speckit.clarify`) до начала кодогенерации.

## 2. Общий контракт как кодовая библиотека (`api-contracts`)

Главный архитектурный вывод проекта: **общий контракт между двумя командами — это сама библиотека `services:api-contracts`**.

Вместо неформальных текстовых соглашений или разрозненных JSON-примеров:
1. **Single Source of Truth**: Все DTO, enum-типы, политики выполнения (`ExecutionPolicy`) и полиморфные ответы проверки (`CheckResult`) определены в общем кодовом модуле.
2. **Типобезопасность на обоих концах**:
   - Бэкенд (Java/Spring Boot) использует скомпилированные классы `api-contracts.jar`.
   - Фронтенд (TypeScript/React) использует автоматически сгенерированные типы `services/api-contracts/ts/taskservice.d.ts` (задача `generateTsApi`).
3. **Защита от дрейфа (Drift Protection)**:
   - Автоматический тест `PolymorphicInvariantGuardTest` гарантирует целостность полиморфных маппингов Jackson при каждом коммите.

## 3. Что согласовали и чему научились при сведении спецификаций

В процессе согласования спек UI (Команда 1) и логики (Команда 2) до и во время интеграции были выявлены три критических момента:

1. **Разрядность чисел и потеря точности в JSON (Seed Safety)**:
   - *Проблема*: Java генерировала 64-битный `long seed` (до $2^{63}-1$), а JavaScript в браузере парсил его как 64-битный `double`, теряя младшие биты. Из-за этого при проверке кода сервер получал искаженный `seed` и запускал проверку с другими параметрами задачи.
   - *Решение*: Ограничение диапазона `seed` на уровне контракта до безопасного `Number.MAX_SAFE_INTEGER` ($2^{53}-1$).

2. **Политика Fail-Fast и формула скоринга**:
   - *Проблема*: Прежняя формула скоринга начисляла 1 балл при наличии 1 ошибки. В режиме fail-fast выполнение теста останавливается сразу на первой ошибке, из-за чего невалидный код ошибочно получал 1 балл вместо 0.
   - *Решение*: В контракте зафиксирована политика `ExecutionPolicy.STOP_ON_FIRST_FAILURE`, а скоринг скорректирован на строгое правило: 0 баллов при наличии любых сбоев.

3. **Специализация шаблонов ввода под типы задач**:
   - *Проблема*: Потоковый ввод последовательности до `0` ломал решение задач на анализ одного числа (16-003, 16-004, 16-005).
   - *Решение*: Контракт и UI адаптируют шаблон и формат входных данных под номер прототипа.
