# spc-demo Constitution

## Core Principles

### I. Изоляция и безопасность исполнения (Sandbox Isolation)
Любой пользовательский и проверяемый код ДОЛЖЕН выполняться исключительно в изолированном окружении (Isolate sandbox с ограничениями по CPU, памяти, таймаутам и процессам). Сервис исполнения обязан расценивать поступающий код как ненадежный. Прямой доступ к хостовой системе или файловой системе за пределами временного рабочего пространства задачи запрещен.

### II. Асинхронный режим работы сервиса (Asynchronous Decoupling)
Тяжелые задачи компиляции, запуска и проверки кода ДОЛЖНЫ выполняться асинхронно. Сервисы не должны блокировать синхронные входящие HTTP-соединения в ожидании завершения прогона. Передача результатов клиентам и смежным сервисам выполняется через асинхронные обратные вызовы (webhooks / callbacks) с уникальными идентификаторами (`attemptId`, `prototypeId`). Приемники ДОЛЖНЫ обрабатывать повторные вызовы идемпотентно.

## Technical Architecture & Constraints

- **Платформа и язык**: Java 26 toolchain под управлением Gradle для всех модулей (`api-contracts`, `task-service`, `code-runner`).
- **Стек сервисов**:
  - `services:api-contracts`: общие DTO, схемы моделей и генераторы контрактов.
  - `services:task-service`: Spring Boot 4.1 для управления задачами и валидации.
  - `services:code-runner`: Javalin 7.2 для запуска песочниц и оркестрации прогонов.
- **Инфраструктура**: Docker Compose стенд (`spc-demo-stand`, cgroup namespaces).

## Development Workflow & Quality Gates

- **Ворота качества (Quality Gates)**:
  - Перед коммитом и мерджем локальный запуск `./gradlew test` ДОЛЖЕН завершаться успешно.
  - При изменении структур API или моделей в `services:api-contracts` обязателен запуск генерации артефактов: `generateApiDocs` и `generateTsApi`.
- **Управление техническим долгом**:
  - Архитектурные компромиссы и временные решения фиксируются в `TECH_DEBT.md`.

## Governance

Данная конституция определяет обязательные базовые правила архитектуры `spc-demo`.

- **Процедура изменений**: Любые изменения принципов и правил согласовываются через pull request с описанием причин и влияния на систему.
- **Политика версионирования**: Используется схема SemVer с пререлизными метками вида `MAJOR.MINOR.PATCH-prerelease` (по образцу `0.1.0-alpha`).
  - MAJOR: критические несовместимые изменения правил или удаление принципов.
  - MINOR: добавление новых принципов, разделов или расширение требований.
  - PATCH: уточнения, стилистические правки и исправления формулировок.
- **Контроль соответствия**: Код-ревью и спецификации проверяются на соблюдение изоляции и асинхронности.
