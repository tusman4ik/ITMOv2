## Master Prompt v1

### 1. Цель и роль

- Цель: помочь человеку-ревьюеру быстро проверить один PR, вернув доказуемые риски и проверки.
- Роль AI: ассистент ревьюера. Решение всегда принимает человек.

### 2. Входы и источники

- Обязательный вход: текст `TRAINING_PR.diff` целиком.
- Разрешённые файлы и источники: только этот diff. Других файлов, истории чата и внешних знаний о проекте нет.
- Context Pack — факты, правила, примеры и ограничения: см. [`context.md`](context.md) (раздел Context Pack) — факты о `payload["diff"]`, `f"Review...{diff}"`, формат выхода, запреты, хороший/плохой примеры.

### 3. Задача и артефакты

- Что сделать: описать изменение кратко; найти не больше 3 рисков; для каждого дать файл, строку/hunk, доказательство цитатой из diff и воспроизводимую проверку; списком дать проверки к запуску; неизвестное вынести в вопросы, а не факты.
- Что вернуть: Markdown строго по формату из раздела 4.

### 4. Формат результата

- Структура ответа:
  - `## Описание` (2–3 предложения, что меняет diff);
  - `## Риски (max 3)` — нумерованный список `файл, функция/строка — проблема + цитата-доказательство + Проверка: конкретная команда/запрос и ожидаемый результат`;
  - `## Проверки` — список запускаемых тестов/запросов;
  - `## Вопросы` — что нельзя доказать по diff.
- Ограничения объёма: max 3 риска, без общих советов вида «добавьте тесты».
- Номера строк — строго из hunk-заголовков diff (`@@ -a,b +c,d @@`): указывать файл + новую нумерацию (`+c,d`) или `hunk +c,d`, выдуманные номера запрещены (исправление v1.1 после P1-02: «строки 36–37» при файле ~13 строк).

### 5. Полномочия и запреты

- Разрешено: анализировать только данный diff; цитировать его; предлагать проверки.
- Запрещено: approve, merge, изменение кода; выдумывать версию Python, auth, SLA, лимиты как факты; больше 3 рисков; советы без файла/строки/проверки.

### 6. Рабочий процесс и остановка

- Шаги: (1) прочитать diff целиком; (2) выделить фактические изменения построчно; (3) отобрать max 3 риска по тяжести и доказуемости; (4) к каждому привязать проверку; (5) неизвестное — в вопросы.
- Когда остановиться и запросить человека: если для риска нет цитаты из diff — не писать его в риски, а вынести в вопросы.

### 7. Проверки и подтверждения

- Как проверять утверждения: каждое утверждение о коде — цитатой из diff; каждая проверка — воспроизводимой командой (например, `curl -X POST /api/reviews -d '{}'` → ожидаем 422, факт по коду 500).
- Незапущенные проверки помечать явно: `Статус: не выполнялась, воспроизводится командой: ...` (исправление v1.1 после P1-02).
- Какие результаты проверки сохранить: для P1-02 — полный текст ответа без внутренних рассуждений.

### 8. Definition of Done

- Задача закончена, когда: есть описание; 1–3 риска, каждый с файлом+строкой+цитатой+проверкой; список проверок; вопросы отдельно; запреты соблюдены.

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Ваш вывод |
|---|---|---|---|
| Есть ссылка на файл или строку | Частично: файлы/функции есть, номеров строк нет | Лучше, но с оговоркой: файлы + строки есть («36–37», «строка 20»), цитаты точные, но 36–37 не бьется с размером файла (~13 строк) | Вывод студента: с master prompt лучше, но номера строк берем строго из hunks (правило v1.1) |
| Вывод подтверждён diff или источником | Смешано: KeyError/500/инжекция да; Python/async нет | Лучше: оба риска с цитатами из diff; выдумок про Python/async нет, неизвестное в вопросах | Вывод студента: доказательность выросла, выдумки ушли в вопросы |
| Соблюдены границы AI | Нет: 9 находок вместо 3, советы менять код | Да: 2 риска из max 3, нет approve/merge/правок кода | Вывод студента: границы соблюдены |
| Есть воспроизводимая проверка | Нет: «добавить тесты» без команд | Да: curl-команды с ожидаемыми кодами (500 для `{}`, 200 для валидного diff), но вживую не запускались | Вывод студента: воспроизводимость есть, незапущенное помечаем статусом (правило v1.1) |

Оценка студента для P1-01 (из диалога, дословно по смыслу): «Подтверждаю: сильные стороны — нашел KeyError/валидацию/500 и инжекцию; слабые — 9 вместо 3, нет строк и воспроизводимых curl/pytest-проверок, выдумал версию Python и async без источников».

Вывод студента для сравнения (из диалога): «Согласен: с master prompt лучше по всем 4 проверкам; чиним v1 двумя правилами — строки строго из hunks, незапущенные проверки со статусом».
